## medium: Falsy attachment metadata values crash rendering for Pydantic attachments

id: fnd_sig-feat-library-6e2b79e49b-fac2_ec662857d1
category: bug
confidence: high
triage: confirmed-bug
status: fixed
feature: Python source src/imap_readonly_mcp (feat_library_6e2b79e49b)

evidence:
- src/imap_readonly_mcp/models.py:46-56 (AttachmentMetadata)
- src/imap_readonly_mcp/models.py:110-116 (MessageDetail)
- src/imap_readonly_mcp/server.py:276-283 (_render_attachments)
- src/imap_readonly_mcp/server.py:295-317 (_render_attachments)

MessageDetail.attachments is modeled as a list of AttachmentMetadata Pydantic models, but _render_attachments mixes attribute access with dict-style metadata.get fallbacks using `or`. Valid falsy values such as size=0, an empty filename, or an empty attachment_id cause the expression to evaluate the `.get(...)` fallback on a Pydantic model, which has no get method. A zero-byte attachment is enough to crash attachment rendering, including the size_hint path used for inline mode.

recommendation:
Use a small helper that reads from mappings with get and otherwise uses getattr without treating falsy values as missing. Only fall back when the value is actually None or absent.

test analysis:
No attachment rendering tests were included, and the edge case requires a valid but falsy metadata value such as a zero-byte attachment.

suggested regression test:
Add a _render_attachments or mail_fetch regression test with a zero-byte AttachmentMetadata and assert the attachment is returned with size 0 without raising.

minimum fix scope:
Replace the mixed `getattr(...) or metadata.get(...)` accesses in _render_attachments with type-aware metadata access.

repro:
Return a MessageDetail whose attachments contain AttachmentMetadata(attachment_id='a', filename='empty.txt', size=0). Calling mail_fetch with include_attachments='meta' or 'inline' reaches _render_attachments and attempts metadata.get('size') on the model.

## medium: HTML entity unescaping can make visible text disappear

id: fnd_sig-feat-library-c7088a8948-a3a7_c7b3561e9d
category: bug
confidence: high
triage: confirmed-bug
status: fixed
feature: Python source src/imap_readonly_mcp/utils (feat_library_c7088a8948)

evidence:
- src/imap_readonly_mcp/utils/email_parser.py:269-293 (_html_to_text)

_html_to_text unescapes entities before stripping tags. Escaped user-visible text such as `2 &lt; 3 and 4 &gt; 1` becomes `2 < 3 and 4 > 1`, then _strip_html treats the `< ... >` span as an HTML tag and removes it. This corrupts generated plain-text bodies and snippets for normal HTML content containing escaped angle brackets.

recommendation:
Strip actual HTML tags before entity-unescaping the remaining text, or replace the custom stripper with an HTML parser that preserves text nodes and then unescapes text content.

test analysis:
tests/test_email_parser.py only covers a plain-text message body and does not exercise HTML-to-text conversion or escaped angle-bracket entities.

suggested regression test:
Add an HTML-only message containing `2 &lt; 3 and 4 &gt; 1` and assert extract_body/create_summary preserves `2 < 3 and 4 > 1` in the text/snippet.

minimum fix scope:
Change _html_to_text ordering or parsing so entity decoding happens after tag removal on text content.

## medium: IMAP all-folder pagination drops results when offset is used

id: fnd_sig-feat-library-df1e19bd2d-2b46_f4f8203950
category: bug
confidence: high
triage: confirmed-bug
status: fixed
feature: Python source src/imap_readonly_mcp/connectors (feat_library_df1e19bd2d)

evidence:
- src/imap_readonly_mcp/connectors/imap.py:223-264 (IMAPReadOnlyConnector.search_all_folders)

search_all_folders computes remaining_budget as limit + offset, but each folder query is capped to min(remaining_budget, limit). With offset=10 and limit=10, a folder with many newest messages contributes only 10 summaries, then the final offset removes them all, so messages 11-20 from that folder are never considered. minimum fix scope:
Adjust per-folder limit calculation in IMAPReadOnlyConnector.search_all_folders and cover offset pagination.

## medium: Invalid cursor values can escape the tool-level error handling

id: fnd_sig-feat-library-6e2b79e49b-4ef9_039e38e2b4
category: bug
confidence: high
triage: confirmed-bug
status: fixed
feature: Python source src/imap_readonly_mcp (feat_library_6e2b79e49b)

evidence:
- src/imap_readonly_mcp/server.py:124-132 (_decode_cursor_value)
- src/imap_readonly_mcp/server.py:506-513 (mail_fetch)

mail_fetch expects cursor decoding failures to be converted into a structured MailFetchResult error, but _decode_cursor_value only catches ValueError, JSONDecodeError, and UnicodeDecodeError. base64 decoding can also raise binascii.Error for malformed padding, and cursor.encode('ascii') can raise UnicodeEncodeError for non-ASCII cursor strings. Those exceptions bypass the ValueError handler in mail_fetch and can fail the whole MCP request instead of returning a normal tool error.

recommendation:
Catch binascii.Error and UnicodeEncodeError in _decode_cursor_value and re-raise ValueError('Invalid cursor payload') so all malformed cursors follow the existing structured error path.

test analysis:
No linked tests were included for malformed cursor handling; the shown code only demonstrates the intended ValueError recovery path.

suggested regression test:
Add a mail_fetch test that passes cursor='abc' and another non-ASCII cursor, asserting the response contains an errors entry instead of raising.

minimum fix scope:
Update _decode_cursor_value exception handling and add focused cursor validation tests.

repro:
Call mail_fetch with cursor='abc' to trigger incorrect base64 padding, or with a non-ASCII cursor string to trigger UnicodeEncodeError before the JSON parsing path.

## medium: Attachment rendering assumes every metadata object is dict-like

id: fnd_sig-feat-cli-command-4e6896962a-_4bcf7187ad
category: bug
confidence: medium

status: open

evidence:
- src/imap_readonly_mcp/server.py:276-282 (_render_attachments)
- src/imap_readonly_mcp/server.py:286-295 (_render_attachments)

_render_attachments iterates over attachment metadata that can come from detail.attachments or rebuilt parser results, then repeatedly evaluates expressions like getattr(metadata, 'attachment_id', None) or metadata.get('attachment_id'). If metadata is a Pydantic/model object without a .get method and the attribute is absent or has a falsy value, the fallback calls metadata.get and raises AttributeError. That can break mail_fetch for messages with attachment metadata objects instead of dictionaries, especially when optional fields are missing or zero-sized.

recommendation:
Normalize metadata access through a small helper that checks mapping types before calling .get, or convert attachment metadata to dictionaries/models consistently before rendering.

test analysis:
No linked tests are included, and the excerpt does not show coverage for object-style attachment metadata with missing optional fields.

suggested regression test:
Add a mail_fetch attachment test using a simple object/model attachment with missing optional fields and assert metadata rendering succeeds without AttributeError.

minimum fix scope:
Refactor the metadata field lookups in _render_attachments to avoid unconditional .get fallback on non-mapping objects.

repro:
Return an attachment metadata object without a get method and with a missing or falsy attachment_id/filename/size/content_type/resource_uri from service.fetch_message or extract_attachments, then call mail_fetch with include_attachments='meta' or 'inline'.

## medium: POP3 uses transient message numbers as stable UIDs

id: fnd_sig-feat-library-df1e19bd2d-7655_7d69e82372
category: bug
confidence: medium
triage: risk
status: open
feature: Python source src/imap_readonly_mcp/connectors (feat_library_df1e19bd2d)

evidence:
- src/imap_readonly_mcp/connectors/pop3.py:95-101 (POP3ReadOnlyConnector.search_messages)
- src/imap_readonly_mcp/connectors/pop3.py:108-131 (POP3ReadOnlyConnector.fetch_message)

Search results expose uid as the POP3 message index, and later fetches convert that uid back to an index for RETR. POP3 message numbers are session-order positions and can change when mailbox contents change, so a search result link can fetch a different message or fail after another client deletes mail. POP3 provides UIDL for stable IDs, but this connector does not use it.

recommendation:
Use POP3 UIDL values as exposed message UIDs, maintain a UIDL-to-index lookup per operation when fetching, and keep the current numeric index only as an internal retrieval detail.

test analysis:
No linked POP3 tests are included, and the issue requires simulating mailbox renumbering between search and fetch.

suggested regression test:
Fake a POP3 server where UIDL values remain stable while message numbers shift between search and fetch, and assert fetch_message retrieves by UIDL rather than by stale index.

minimum fix scope:
Change POP3 summary UID generation and fetch/raw/attachment lookup to resolve UIDL to the current message number.

## low: Fragile environment variable detection via env parsing

id: fnd_sig-feat-config-19c6c52003-41f2e_a705de7120
category: bug
confidence: high
triage: confirmed-bug
status: open
feature: Shell/workflow config run-streamable-http.sh (feat_config_19c6c52003)

evidence:
- scripts/run-streamable-http.sh:60-65

The script attempts to detect if any environment variables starting with 'MAIL_ACCOUNT__' are set by parsing the output of the 'env' command. This approach is fragile because 'read' combined with 'env' output does not correctly handle environment values containing newlines. If a variable contains a newline followed by a string starting with 'MAIL_ACCOUNT__', the script will incorrectly conclude that an account is configured via environment variables. While this only affects the 'friendly' error message logic, it is less robust than using Bash's built-in variable prefix expansion.

recommendation:
Use Bash's built-in indirect expansion to check for variables with a specific prefix: 'if [[ -n "${!MAIL_ACCOUNT__*}" ]]; then ACCOUNT_ENV_CONFIGURED="true"; fi'.

test analysis:
There are no tests provided for this shell script in the project.

suggested regression test:
A test case that executes the script with a multiline environment variable that does not contain a real account configuration, verifying that the script still identifies the configuration as missing.

minimum fix scope:
Replace the 'while' loop block (lines 60-65) with a single conditional using Bash prefix expansion.

repro:
Run the script with an environment variable containing a newline that mimics the prefix, e.g., 'export SPOOF=$"foo\nMAIL_ACCOUNT__ANY=1"; scripts/run-streamable-http.sh'. The script will bypass the missing config check even if no real account variables exist.

## low: Potential for incorrect PROJECT_ROOT if command substitutions fail

id: fnd_sig-feat-config-19c6c52003-4eb12_d9b49af6a4
category: maintainability
confidence: medium
triage: risk
status: open
feature: Shell/workflow config run-streamable-http.sh (feat_config_19c6c52003)

evidence:
- scripts/run-streamable-http.sh:20-21

The script uses command substitutions to determine SCRIPT_DIR and PROJECT_ROOT. Under 'set -e', if a command inside a substitution fails (like 'cd' to a non-existent or restricted directory), the shell script does not immediately exit unless 'shopt -s inherit_errexit' is set (which is not standard in many Bash versions or this script). Instead, the variable is assigned an empty string. This can lead to PROJECT_ROOT being incorrectly resolved to the filesystem root ('/'), causing subsequent checks and 'exec' attempts to look in incorrect locations.

recommendation:
Use separate commands to change directories and capture 'pwd', or set 'shopt -s inherit_errexit' if the environment allows Bash 4.4+. Alternatively, verify that SCRIPT_DIR is non-empty after assignment.

test analysis:
No tests are provided for the wrapper scripts.

minimum fix scope:
Add a check to ensure SCRIPT_DIR and PROJECT_ROOT are not empty after assignment.

repro:
This is difficult to trigger without environmental issues (e.g., executing the script from a context where its own directory is unreadable), but would result in PROJECT_ROOT being assigned '/' if the first 'cd' fails.
