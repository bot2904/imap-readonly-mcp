Verify that the codebase is strictly read-only and audit mailbox filtering behavior across all supported mail protocols. This is an investigation/reporting task only: gather enough information to create a later implementation plan, but do not implement fixes as part of this todo.

## Scope

- Protocols/connectors in scope: IMAP, POP3, Microsoft Graph, and any Gmail-related configuration or connector paths present in the repo.
- Access paths in scope:
  - `mail_fetch` search/list/read flows
  - direct message-id fetches via `ids`
  - `mail_download_attachment`
  - MCP resources:
    - `mail://{folder_token}/{uid}`
    - `mail+html://{folder_token}/{uid}`
    - `mail+raw://{folder_token}/{uid}`
    - `mail+attachment://{folder_token}/{uid}/{attachment_identifier}`
    - `mail://folders`
  - cache reads/writes and any cached data reuse

## Expected Folder Filtering Semantics to Audit Against

- `allowed_folders` is an exact allow-list: only exact matching folders are accessible; everything else is denied/hidden.
- `excluded_folders` overrides `allowed_folders` when both match.
- Folder matching should be case-insensitive.
- Folders outside the effective allow-list must never be exposed anywhere:
  - not in folder listings
  - not in search/list results
  - not through direct fetch by folder token/message id
  - not through raw/html/text resources
  - not through attachment resources or attachment download tooling
  - not through cache hits from previously accessible folders
- If a denied folder/message is requested directly, behavior should be indistinguishable from a missing folder/message to the user, while logging audit information internally.

## Verification Tasks

- [ ] Audit all connectors (`imap`, `pop3`, `graph`, and any Gmail-related code paths/config hooks) for mutating operations such as IMAP `STORE`/`DELETE`/non-PEEK fetch side effects, POP3 deletes, and Graph/Gmail write APIs (`POST`, `PATCH`, `DELETE`, label/status mutations, etc.).
- [ ] Confirm IMAP uses `BODY.PEEK` consistently in every fetch path and does not mark messages as read.
- [ ] Check service, server, middleware, and cache layers for write-like behavior that could affect the mailbox or leak previously accessible data.
- [ ] Trace how `allowed_folders` and `excluded_folders` are currently parsed, normalized, and applied, if at all.
- [ ] Determine whether filtering is implemented at the connector layer, service layer, server/resource layer, or only documented/configured.
- [ ] Audit all direct resource and attachment access paths for folder filtering enforcement before cache reads and before connector calls.
- [ ] Audit all search/list flows for folder filtering enforcement, including all-folder search heuristics such as archive/all-mail selection.
- [ ] Audit cache behavior to determine whether cached messages from now-disallowed folders can still be returned.
- [ ] Identify expected logging points for denied folder/message access while preserving user-facing “not found” semantics.
