Verify that the codebase is strictly read-only and audit mailbox filtering behavior across all supported mail protocols. This is an investigation/reporting task only: gather enough information to create a later implementation plan, but do not implement fixes as part of this todo.

## Scope

- Protocols/connectors in scope: IMAP, POP3, Microsoft Graph, and any Gmail-related configuration or connector paths present in the repo.
- Access paths in scope:
  - `mail_fetch` search/list/read flows
  - direct message-id fetches via `ids`
  - `mail_download_attachment`
  - MCP resources:
    - `mail://{folder_token}/{uid}`
    - `mail+html://{folder_token}/{uid}`
    - `mail+raw://{folder_token}/{uid}`
    - `mail+attachment://{folder_token}/{uid}/{attachment_identifier}`
    - `mail://folders`
  - cache reads/writes and any cached data reuse

## Expected Folder Filtering Semantics to Audit Against

- `allowed_folders` is an exact allow-list: only exact matching folders are accessible; everything else is denied/hidden.
- `excluded_folders` overrides `allowed_folders` when both match.
- Folder matching should be case-insensitive.
- Folders outside the effective allow-list must never be exposed anywhere:
  - not in folder listings
  - not in search/list results
  - not through direct fetch by folder token/message id
  - not through raw/html/text resources
  - not through attachment resources or attachment download tooling
  - not through cache hits from previously accessible folders
- If a denied folder/message is requested directly, behavior should be indistinguishable from a missing folder/message to the user, while logging audit information internally.

## Audit Report — 2026-06-09

### Executive Summary

The codebase is largely read-only with respect to remote mailboxes, but folder filtering is effectively **not implemented**. `allowed_folders` and `excluded_folders` are parsed into configuration only; no connector, service, tool, resource, or cache path enforces them. This creates high-risk bypasses through folder listing, all-folder search, direct `ids`, MCP resources, attachment downloads, and cached message bodies.

### Read-only Guarantees

**IMAP — acceptable / low risk**

- `IMAPReadOnlyConnector._select_mailbox()` uses `conn.select(..., readonly=True)` (`src/imap_readonly_mcp/connectors/imap.py:369-373`).
- Full message, raw, attachment, and summary fetches use `BODY.PEEK` (`imap.py:266-310`, `imap.py:331-334`, `imap.py:394-395`), so they should not set `\Seen`.
- Search uses `UID SEARCH` (`imap.py:380-385`) and folder listing uses `LIST` (`imap.py:161-195`).
- No `STORE`, `EXPUNGE`, `DELETE`, `COPY`, or flag mutation calls were found.

**POP3 — acceptable / low risk**

- POP3 uses `STAT` and `RETR` only for mailbox reads (`src/imap_readonly_mcp/connectors/pop3.py:83-90`, `pop3.py:152-154`).
- No `DELE` calls were found. `quit()` is issued (`pop3.py:67-69`), but this only commits deletions already requested in the same session; this connector never requests any.

**Microsoft Graph — mostly acceptable / low risk for mailbox mutation**

- Mailbox API access uses `GET` calls for folders, messages, raw `$value`, and attachments (`src/imap_readonly_mcp/connectors/graph.py:60-92`, `graph.py:94-125`, `graph.py:132-140`, `graph.py:173-200`).
- No Graph `POST`, `PATCH`, or `DELETE` mailbox mutation calls were found.
- MSAL token acquisition (`graph.py:246-255`) may perform OAuth token HTTP calls outside the connector session, but these are auth operations rather than mailbox mutations.

**Gmail-related paths — configuration only**

- There is no Gmail protocol enum or connector. The only Gmail-specific hook found is `google_service_account_json` on `MailAccountConfig` (`src/imap_readonly_mcp/config.py:145-148`), which is not wired into `MailService._get_connector()` (`src/imap_readonly_mcp/service.py:113-123`). No Gmail API reads or writes were found.

**Local write-like behavior**

- The service writes message details to a local SQLite cache (`src/imap_readonly_mcp/service.py:281-338`). This is not a mailbox mutation, but it is security-relevant because cached data can outlive current folder policy.

### Folder Filtering Findings

**Finding 1 — `allowed_folders` / `excluded_folders` are parsed but never enforced (HIGH)**

- Config fields exist at `src/imap_readonly_mcp/config.py:115-122` and tests only verify parsing (`tests/test_config.py:13-34`).
- No enforcement references were found outside config/docs/tests.
- Effective behavior today: all folders the connector can see are exposed and searchable regardless of configured allow/block lists.

Affected paths:

- `MailService.list_folders()` directly returns connector folders (`service.py:49-51`).
- `MailService.search_messages()` delegates directly after normalization (`service.py:53-58`).
- `MailService.fetch_message()`, `fetch_raw_message()`, `fetch_attachment()`, and `fetch_details_bulk()` perform no policy check (`service.py:60-110`).
- `mail://folders` exposes unfiltered folders (`server.py:880-887`).
- Direct `mail_fetch(ids=...)` accepts any folder token and UID (`server.py:540-562`).
- `mail_download_attachment` and MCP resources call service fetch methods directly (`server.py:728-746`, `server.py:769-818`).
- Diagnostic `mail_debug_list_parts` is also an unfiltered raw-message access path (`server.py:820-833`).

**Finding 2 — all-folder search and all-mail heuristic ignore filtering (HIGH)**

- `_search_all_folders()` lists every selectable folder (`service.py:171-189`) and either searches the inferred all-mail/archive folder (`service.py:183-187`) or iterates every folder (`service.py:201-216`).
- If a policy later filters only list output but not this method, search would still leak disallowed folders.
- The IMAP connector also has its own unfiltered `search_all_folders()` (`imap.py:218+`), currently not called by service but risky if reused later.

**Finding 3 — cache can bypass future policy unless policy is checked before cache reads (HIGH)**

- `fetch_message()` returns `_cache.get(folder_token, uid)` before decoding/checking the folder (`service.py:60-63`).
- `fetch_details_bulk()` does the same for each request (`service.py:88-93`).
- Cached messages from a folder that becomes disallowed would still be returned by direct id/resource access unless enforcement happens before cache lookup and cached payload validation.

**Finding 4 — direct resource/attachment paths expose decoded folder tokens without policy (HIGH)**

- `fetch_raw_message()` and `fetch_attachment()` decode the user-supplied token and call the connector directly (`service.py:68-81`).
- `mail://...`, `mail+html://...`, `mail+raw://...`, and `mail+attachment://...` resources delegate to these methods with no separate guard (`server.py:769-818`).
- User-facing errors are currently connector exceptions; denied access is not made indistinguishable from missing because denial does not exist.

**Finding 5 — Graph direct message fetch can ignore the folder token (HIGH)**

- `GraphReadOnlyConnector.fetch_message()`, `fetch_raw_message()`, and `fetch_attachment()` use `/messages/{uid}` and `/messages/{uid}/attachments` rather than folder-scoped URLs (`graph.py:94-95`, `graph.py:173-183`).
- The `folder_path` parameter is not used to constrain the fetch. A caller could present an allowed folder token with a message id from a disallowed folder and still retrieve the message unless the returned `parentFolderId` is checked or folder-scoped endpoints are used.
- Raw and attachment fetches do not inspect the parent folder at all before returning data.

**Finding 6 — POP3 ignores requested folder path (MEDIUM)**

- POP3 has a virtual `INBOX` only (`pop3.py:71-81`), but `fetch_message()`, `fetch_raw_message()`, and `fetch_attachment()` ignore `folder_path` and retrieve by numeric UID (`pop3.py:108-135`).
- If `INBOX` is excluded, or if a non-INBOX token is supplied, there is no policy or token validation to prevent access.

**Finding 7 — no case-insensitive exact matching or exclude-overrides-allow semantics exist (HIGH)**

- There is no normalization/casefold function and no effective allow-list computation.
- Exact matching semantics are undocumented in code; README examples only show fields (`README.md:119-120`).

**Finding 8 — denied-access audit logging is absent (MEDIUM)**

- No folder-policy denial points exist. Recommended behavior (“not found” to user, audit internally) is currently impossible to satisfy.

### Recommended Implementation Plan

1. Add a central folder policy component in the service layer, derived from `settings.account.allowed_folders` and `settings.account.excluded_folders` using `str.casefold()` exact matching. Treat `None` allow-list as “all except excluded”; excluded must override allowed.
2. Apply the policy in `MailService` before every cache read and connector call: `list_folders`, `search_messages`, `_search_all_folders`, `fetch_message`, `fetch_details_bulk`, `_fetch_message_uncached`, `fetch_raw_message`, and `fetch_attachment`.
3. Filter folder listings before returning them and ensure all-mail/archive folder selection only considers allowed folders.
4. For direct access denial, raise the same public not-found exception shape used for missing folder/message/attachment, but log an internal warning/audit event with protocol, normalized folder, operation, and uid/attachment id where available.
5. Fix Graph direct fetch semantics: either use folder-scoped endpoints where possible or verify the fetched message’s `parentFolderId` against the decoded token and policy before returning/caching. Raw and attachment fetches need an equivalent parent-folder check before bytes leave the connector/service.
6. Validate POP3 folder tokens: only the virtual `INBOX` should be acceptable, and the policy should be applied to `INBOX` before any POP3 `RETR`.
7. Harden cache: policy-check the decoded token before `_cache.get`; validate cached `MessageDetail.folder_path` still passes policy and matches the requested token; ignore or purge stale/denied cache rows.
8. Consider adding `display_name` to Graph `FolderInfo` or explicitly document that folder allow/exclude values for Graph are folder IDs, because current `FolderInfo.path` is Graph’s opaque folder id while `_infer_folder_role()` uses display names.

### Test Requirements Identified

- Config/env parsing for `MAIL_ACCOUNT__ALLOWED_FOLDERS` and `MAIL_ACCOUNT__EXCLUDED_FOLDERS`.
- Case-insensitive exact matching (`INBOX` allows `inbox`, but not `Inbox/Sub`).
- Exclude-overrides-allow when both include the same folder.
- `mail://folders` hides disallowed folders.
- Search/list with explicit folder rejects hidden folders as not found/empty and never returns disallowed folders.
- All-folder search and all-mail/archive heuristic only use allowed folders.
- Direct `mail_fetch(ids=[...])`, text/html/raw resources, `mail_download_attachment`, attachment resources, and `mail_debug_list_parts` behave as not found for denied folders.
- Cache hit cannot bypass a newly disallowed folder.
- Graph-specific direct-id test where the supplied folder token is allowed but the fetched message’s `parentFolderId` is disallowed/mismatched.
- POP3-specific test where `INBOX` is excluded and all fetch/list/search paths deny/hide it.
